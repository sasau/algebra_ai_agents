# LAB-101 — Tokenizer mishandles CRLF line endings

Read this supplied bug report before starting the lab. **LAB-101 is its identifier**: the name used to select this report from the lab database. **Reproduction instructions from the report:**

> Run the tokenizer suite against "1 + 2\r\n". A carriage return is not skipped and the CRLF test fails. Inspect fixture/src/tokenizer.ts.

**Expected behavior from the report:**

> Both LF and CRLF endings are whitespace. Tokenization must produce the same numbers and operators.

The notation `\r\n` represents two actual newline characters: carriage return followed by line feed. It does not mean that an ordinary expression contains four backslash/letter characters. The tokenizer should treat these newline characters as whitespace instead of rejecting the expression.

## Locate the source and reproduction test

In your editor, open these two files from the `practice-02/` folder:

1. [fixture/src/tokenizer.ts](../fixture/src/tokenizer.ts). Find `tokenize(source: string)`. It reads expression text one character at a time and returns numbers, operators and parentheses. Find the branch that handles `char === "\n"` and the later `SyntaxError` branch. The source handles line feed but does not skip carriage return.
2. [fixture/test/tokenizer.test.ts](../fixture/test/tokenizer.test.ts). Find the test named **`tokenizer normalises CRLF line endings`**. It compares the same expression split over two lines using the two newline forms:

```ts
assert.deepEqual(tokenize("1\r\n+ 2"), tokenize("1\n+ 2"));
```

The report shows an expression with a newline at the end; the exact supplied test places the newline between `1` and `+ 2`. Both examples expose the same unsupported carriage-return character. The test expects the two token arrays to match.
