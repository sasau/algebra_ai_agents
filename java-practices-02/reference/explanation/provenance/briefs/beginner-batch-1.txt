Define each unfamiliar concept with everyday meaning before relying on it. Explain
who calls which method, who runs code, who waits, what changes and what can fail.
Use caller=thread making a method call; worker=thread running the assigned work;
task=code to perform. Explain these in slide2. Explain platform thread as Java
thread normally backed by an OS thread before virtual comparison. Avoid shorthand
such as execution path, operation boundary, invariant, candidate, resource policy,
receipt, liveness, observable outcome, admission, cancellation cooperation without
first explaining the actual action/state. If a technical name matters, define it
in plain language then keep the precise name. Do not omit difficult concepts.
First-person course voice is unnecessary. Keep prepared agents/setup brief.

CRITICAL Thread semantics: for the plain platform Thread created with Runnable
task, worker.start() asks Java to start a new thread. Java runs worker.run() on
that new thread; the default Thread.run() calls task.run(). start() is NOT an
ordinary direct call to task.run() on the caller. Direct worker.run() in this
platform example calls task.run() on the CALLER, with no new thread. Explain this
explicitly in slides6-10 and lifecycle pages. Calling virtual Thread.run directly
does not execute its task, so do not generalize direct-run to virtual threads.
Constructor/builder unstarted does not execute task. Each Thread starts once.
join waits on CALLER for target termination, not worker waiting for caller. A
successful join of a started worker establishes termination/visibility; join on
an unstarted platform Thread returns immediately. None of start/run/join returns
task result. Timed join can return while target alive; join(0) is untimed.
isAlive false also before start. interrupt requests cooperation, never force-kill.

Other critical facts: monitor entry contenders BLOCKED, not Object.wait waitset;
endless monitor owner is indefinite blocking without necessarily deadlock cycle;
all accesses must share same monitor; volatile is not an atomic increment;
AtomicInteger does not make separate get/check/decrement one atomic decision;
executor queue stores tasks, blocking queue stores items; fixed pools have an
unbounded queue; one-worker parent+child get can deadlock; Future.get wraps failure
in ExecutionException; cancelled Future.get throws CancellationException; this
aggregator checks isCancelled then throws its OWN TimeoutException; timed get does
not cancel, timed invokeAll cancels unfinished tasks; cancellation != worker stop;
semaphore acquire BEFORE try, release in finally after success, no owner/max-cap
enforcement; ReentrantLock only owner unlocks, timed tryLock false no ownership;
Java21 synchronized blocking can pin virtual carriers; JDK24 JEP491 removes
monitor-related pinning; native cases remain. Queue waiting releases INTERNAL
lock, not unrelated outer monitor. Global fork order avoids circular deadlock,
does not prove starvation freedom. Timing no universal speedup or speed assertions.
Do not add unimplemented runtime/test claims. APIs/exceptions must stay exact.
