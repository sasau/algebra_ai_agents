2. The problem: starting is not completion

We want a console example that returns the actual executing worker name. The caller starts a platform worker, which records its name into a shared result. If the caller reads immediately, that read can happen before the worker stores anything. This timeline illustrates one possible schedule; it is not a recorded unsafe run or a method supplied by the reference.

3. The solution: start, join, then read

The caller calls worker.start(). Java starts the platform worker, which executes worker.run(); its default implementation calls the supplied task’s run() method. The caller continues without waiting. It then calls worker.join() to wait until the worker ends. After that call returns normally, the worker’s changes are visible to the caller, which reads the result. In the separate direct-call case, worker.run() executes the task on the calling thread and records that caller’s name.

Thread worker = Thread.ofPlatform().name("unused-worker").unstarted(
        () -> result.set(Thread.currentThread().getName()));

It uses the same shape, with a fresh AtomicReference and the name unused-worker. It calls run() instead of start().

What is shared

Only the AtomicReference is shared. The lambda keeps access to this same container; this is called capturing a variable. The caller and the worker both hold a reference to the same object.

What start schedules

start makes a new execution path eligible to run. It does not say when the path runs, how fast, or in what order its output appears relative to the caller.

What join guarantees

When join returns normally, the worker has terminated. The Java memory model also says that every action in the worker happens-before a successful return from join on that thread. The caller therefore sees the worker's writes. Here the written value is the name, and the caller reads it after the join.

Why run stays on the caller

run() is an ordinary method call on a Thread object. It starts nothing. The lambda executes inside the calling thread, so Thread.currentThread().getName() returns the caller's name. The name unused-worker is never observed.

What AtomicReference guarantees independently

AtomicReference gives atomic and visible get and set operations on that one reference. Taken alone, it would make the stored value safely visible. It does not make the caller wait. Without join, the caller could read null because the worker had not run yet. Visibility and completion are separate properties here, and join supplies completion.

Why the thread name is evidence, not synchronization

The name is data the task records about itself. It shows who executed the task. It does not order anything and does not make anything visible. Only join and the atomic type do that work.

7. Errors, interruption and timeouts

  • join throws InterruptedException if the caller is interrupted while waiting. startAndJoin declares it and does not hide it. In that case the worker's completion was not established.
  • join() has no inherent timeout. If the worker never ends, the caller waits forever.
  • The test's @Timeout(15) is a guard that fails a hung test after 15 seconds. It is not a runtime guarantee that startAndJoin will return in production use.
  • After a repair, rerun the same focused test first. Run the Main route again and refresh the HTML using the repaired source and fresh execution evidence before advancing.

Concurrency — four problems when tasks overlap

A task is code to perform. A thread runs code. The caller is the thread making a method call; a worker runs assigned work. Concurrency means tasks overlap in time. Parallelism means they run at the same moment. Overlapping tasks need coordination: wait for completion, change shared data safely, report results or failures, and share limited resources such as locks or database connections.

Java feature and limits: Knowing when work finished, updating data safely, reporting failures and making progress each need their own check. A program that compiles successfully proves none of them.

Thread — create an object before starting its work

Thread is a Java class that provides a run() method. new Thread(task, name) creates an object representing an unstarted platform thread: a Java thread backed by an operating-system thread. The task parameter supplies a Runnable object; name labels the thread. new produces a reference stored in worker. Construction does not execute the task. Call worker.start() separately to start the new thread.

Java feature and limits: These are Java 21 API excerpts. The reference uses Thread.ofPlatform().name(name).unstarted(task), which also creates an unstarted platform thread. A Thread object can be started only once.

Runnable — define the work with a lambda

Runnable is an interface describing work through run(). This method has no parameters, and void means it returns no value. Its declaration has no body: an implementation supplies the statements to execute. A functional interface has one abstract method, so a lambda can supply that implementation. In Runnable task = () -> { ... }, the empty parentheses match run(), the arrow introduces its body, and the braces contain its statements.

Java feature and limits: Assigning the lambda defines work without running it. A class can also implement Runnable with public void run(). That method declares no checked exceptions; its body must handle any checked exception itself.

Thread — start(), run() and join() do different jobs

The caller calls worker.start(). Java starts the platform worker, which executes worker.run(); its default implementation calls the supplied task.run(). The caller continues without waiting. Calling worker.run() directly instead runs the task on the caller, creating no new thread. worker.join() makes the caller wait until the worker ends. All three return void, so none returns a task value. After untimed join() returns normally, the worker’s changes are visible to the caller.

Java feature and limits: Call start() before join(): joining an unstarted platform thread returns immediately. A second start() throws IllegalThreadStateException. InterruptedException from join() means the waiting caller was interrupted; it does not cancel the worker.

Thread — timed join, interrupt and state checks

join() with a positive millisecond value limits the caller’s wait. Its void return does not distinguish a finished worker from a timeout, so check isAlive(). interrupt() asks the target thread to cooperate; it never forces a stop. isInterrupted() reads the target’s interrupt status without clearing it. A worker can check this flag between short pieces of work. isAlive() is true only after the thread starts and before it ends.

Java feature and limits: join(0) waits without a time limit. isAlive() is also false before start and does not prove success. Interrupting a thread waiting in sleep(), wait() or join() makes that call throw InterruptedException and clears its interrupt status.

Thread — connect the task, worker and result

The Runnable object describes the work. The Thread object represents the worker that will run it. Creating an unstarted Thread runs no task code. worker.start() starts a new thread; the default platform Thread.run() calls task.run() there. worker.join() makes the caller wait until that worker ends. The task stores its result separately. Follow the diagram from task definition to starting, waiting and reading.

Java feature and limits: A Thread can be started only once. In this platform-thread example, calling worker.run() directly runs task.run() on the caller. Directly calling run() on a virtual Thread does not execute its task.

Thread — a worker that never ends keeps join() waiting

If a worker never ends, the caller can wait in join() forever. The illustrated loop has no circle of threads waiting for each other; it fails because it never finishes. Design the worker to stop: do finite pieces of work, check for an interrupt request, and leave through cleanup. A timed join() limits the caller’s wait. Then isAlive() checks whether the worker actually stopped.

Java feature and limits: This is an illustrative failure, not the finite lifecycle task in the supplied project. Interrupting and timed join cannot force an arbitrary worker to stop.

CyclicBarrier and CountDownLatch — waiting and signalling

A CyclicBarrier makes a fixed number of peer threads wait for each other at a meeting point. It can be reused. In the counter example, both workers finish reading before either writes. A CountDownLatch counts one-time signals down to zero. A caller waiting on it continues only at zero. Each mechanism has a participant count, a waiting point and a release condition. Neither collects a task’s value or reports its exception.

Java feature and limits: The lost-update example uses a barrier. The dining example uses latches. A completion signal does not prove the work succeeded, so check failures separately.

CyclicBarrier and CountDownLatch — handle missing signals

A missing participant can prevent coordination from finishing. If B fails before reaching the barrier, A can wait forever. If a worker forgets its latch signal, the count may never reach zero. Use timed waits and check task failures separately. Signalling a latch in finally can mean the worker ended, including by failure. A barrier timeout breaks that barrier and releases the other waiting threads by throwing an exception.

Java feature and limits: Other threads waiting at the broken barrier receive BrokenBarrierException. Future.get(), introduced later, can report task success or failure. A timeout only reports incomplete coordination; it does not perform the missing work.

Race condition — two workers overwrite one increment

An increment reads the old value, adds one and writes the new value back. A and B can both read zero, then both write one. A barrier makes both reads finish before either write, forcing this lost update. volatile makes a write visible to later reads of that field, with ordering guarantees. It does not combine the read, calculation and write into one indivisible step.

Java feature and limits: The reference deliberately forces this interleaving: the order in which thread actions overlap. A loop that relies on uncontrolled timing may happen to return the expected count and hide the defect.

Synchronized — one monitor owner, other threads wait

A monitor is a lock that every Java object has. The code synchronized (lock) makes a thread acquire the monitor of that object. The braces mark the protected block. One thread owns the monitor. Other threads that want in wait at the entrance, and Java reports their state as BLOCKED. Leaving the block, normally or by exception, releases the monitor. Every protected access must use the same object. Arrival order at the entrance is not promised.

Java feature and limits: Entering synchronized uses the object’s monitor. Threads blocked at entry are separate from the waiting threads created by Object.wait(). A synchronized instance method locks this; a static synchronized method locks its Class object.

Synchronized — an endless loop keeps the monitor locked

Suppose thread A owns a monitor and runs a loop that never ends. Threads B and C stay BLOCKED at the entrance. The monitor is held indefinitely, and this is not necessarily a deadlock, because no circle of waiting exists. An interrupt does not unlock the monitor or stop a loop that ignores it. Do long or blocking work outside the block when the shared data allows. Keep each protected update short and finite.

Java feature and limits: This is an illustrative failure. Thread.sleep also keeps any monitor the thread owns. Entering synchronized has no built-in timed or interruptible version.

Synchronized — opposite lock orders create deadlock

A deadlock is a circle of waiting in which no thread can move. Thread A owns monitor M1 and waits for M2. Thread B owns M2 and waits for M1. Neither can reach the end of its block to release anything. The fix is one global order, such as always M1 before M2. Nested locking can also be removed when it is not needed. Keeping protected work finite is a separate requirement.

Java feature and limits: Interrupting a thread blocked at synchronized entry does not cancel that wait. The later ReentrantLock recovery example uses an API that can be interrupted.

Monitor — protect the whole counter update

A monitor lets one thread at a time run code guarded by that same monitor. Put the counter’s read, calculation and write inside one synchronized block. While A updates, B waits outside. After A releases the monitor, B sees the updated value 1 and writes 2. Serializing means taking turns: either worker may go first, but both increments are counted.

Java feature and limits: Mutual exclusion means only one owner at a time. Releasing the monitor also makes changes visible to the next owner. Every counter access must follow the same locking rule; entry order is not guaranteed.

AtomicInteger — update one counter in an indivisible step

AtomicInteger holds one shared int. Atomic means an operation takes effect as one indivisible step. get() reads the value, set() replaces it, and incrementAndGet() reads, adds one and returns the new value as one atomic operation. Both workers use the same AtomicInteger object. Separate method calls still leave gaps where another thread can act, so several calls do not automatically form one atomic decision.

Java feature and limits: This describes what the API guarantees, not a specific hardware instruction. Atomic operations do not promise scheduling fairness.

AtomicInteger — separate checks and updates can still race

Atomic methods do not make a separate check and update atomic. With one ticket left, A and B can both read 1. Their two decrements then leave -1. compareAndSet(1, 0) changes the value only if it is still 1 and returns whether it succeeded. Only one thread wins; the loser rereads and checks again. The diagram uses CAS (compare-and-set).

Java feature and limits: This ticket scenario illustrates a different problem from the supplied increment example. A monitor around the whole check and decrement, or a correctly paired semaphore, is another solution. Retrying does not guarantee every thread eventually succeeds.

AtomicInteger — count both increments without losing either

AtomicInteger.incrementAndGet() reads the counter and adds one as a single atomic operation. Overlapping calls still take effect in a valid sequence. Here A changes 0 to 1 and B changes 1 to 2. The caller waits for both tasks before checking the total. Neither call can overwrite an increment using a separately saved old value, as the unsafe version did.

Java feature and limits: This order is only one possibility. AtomicInteger does not promise fairness between callers. It does not make a change across several fields atomic.

ExecutorService — separate tasks from the threads running them

ExecutorService accepts tasks and runs them on worker threads. submit() hands over a task and returns a Future, an object used to obtain its eventual result or failure. A fixed pool reuses its workers. Tasks that cannot start yet wait in a queue; the queue holds tasks, not threads. The caller can wait through the Future. When finished, the application must close the executor and check that its workers end.

Java feature and limits: newFixedThreadPool(2) limits workers to two but uses an unbounded task queue. Closing the executor can wait for unfinished tasks. A Future is not a thread.

ExecutorService — limit queued tasks and handle rejected work

Two busy workers do not limit submissions. An unbounded queue has no fixed maximum length, so slow work can cause growing delays and memory use. This ThreadPoolExecutor has two workers and two queue slots. If both workers stay busy and both slots stay full, the next task is rejected: AbortPolicy throws RejectedExecutionException. The caller must handle this, for example with a busy response or a retry before a deadline.

Java feature and limits: This bounded executor is only an explanation. The supplied shop aggregator uses a fixed pool and a small finite input. The rejection policy and caller handling must be designed together.

ExecutorService — waiting tasks can block their own pool

A pool with one worker can deadlock if tasks wait for other tasks in that same pool. A parent runs on the worker, submits a child, then waits for its result with Future.get(). The child cannot run because the parent occupies the only worker. Instead, let an outside caller submit the work and wait, or perform the child work directly. More workers do not solve every nested dependency.

Java feature and limits: This one-worker failure is only an illustration, not the supplied two-worker quotes code. The caller must stay outside the pool whose capacity its awaited tasks need.

Future — distinguish pending, successful, failed and cancelled tasks

A Future stands for a task’s eventual outcome. Calling get() waits, then returns the value or throws an exception for failure or cancellation. isDone() is true for success, failure and cancellation, so it alone does not prove success. A timed get() limits how long the caller waits and does not cancel the task. Timed invokeAll does cancel tasks unfinished at the deadline. The aggregator checks isCancelled() before collecting values.

Java feature and limits: A failed task makes get() throw ExecutionException. Calling get() on a cancelled Future throws CancellationException. The supplied aggregator instead checks isCancelled() and throws its own TimeoutException. Cancellation does not prove the worker stopped.

Future — cancellation does not prove the task stopped

A Future can report cancelled while its task still runs. cancel(true) requests interruption when the task is running; the task must respond for that request to stop it. If it ignores interruption, closing the executor may keep waiting. Use finite work steps, interruptible waits and finally blocks that release resources. After cancelling, wait a limited time for termination and explicitly handle any worker that remains alive.

Java feature and limits: The supplied waits respond to interruption. shutdownNow() requests interruption of running tasks and removes queued tasks, returning them to the caller. It cannot force running tasks to stop or prove cleanup.

ExecutorService — submitting work and finishing it are separate

A Callable is a task whose call() method returns a value or throws an exception. The executor assigns these tasks to workers; each Future holds one eventual result or failure. Here two platform workers serve three simulated shops, so one lookup waits in the queue. After invokeAll() returns, the caller uses get() to read each value or detect failure, then totals the successful quotes.

Java feature and limits: A fixed thread pool limits workers but has an unbounded queue. Large inputs also need a limit on accepted work, or a bounded executor queue.

Task outcomes — return values or report failures and timeouts

The batch can produce values, contain a failed task, or reach its deadline. Future.get() wraps a task exception in ExecutionException and preserves the original cause. Timed invokeAll() cancels unfinished tasks. This aggregator checks isCancelled() and throws its own TimeoutException. The three rows show what the caller receives. Interruption asks a worker to stop, so cleanup must still confirm that workers actually end.

Java feature and limits: Cancelling a Future does not prove its worker stopped. Closing an executor can wait if tasks ignore interruption. The lesson tasks respond to interruption.

Virtual threads — run on carriers and release them when waiting

A virtual-thread executor creates one virtual thread per task. A virtual thread is a lightweight Java thread. To execute, Java mounts it on a carrier: a platform thread backed by an operating-system thread that can run on a processor. During supported blocking operations, the virtual thread can unmount, freeing the carrier. Its identity and saved execution state remain. Later it can resume on an available carrier, possibly a different one.

Java feature and limits: The carrier count shown is only an illustration. Virtual threads add no processor cores, database connections or correctness guarantees. Create one per task instead of pooling them.

Virtual threads — pinning keeps a carrier occupied

On Java 21, blocking inside synchronized can keep a virtual thread attached to its carrier. This is pinning: other virtual threads cannot use that occupied carrier. Keep synchronized sections short and move blocking work outside when correctness allows. ReentrantLock can support blocking coordination on Java 21 without this monitor pinning. JDK 24 removes monitor-related pinning; some native-code cases remain. Separately, use a semaphore to limit scarce database or service capacity.

Java feature and limits: The version change is JEP (JDK Enhancement Proposal) 491 in JDK 24. Pinning is not a circular deadlock. Upgrading Java does not increase an outside service’s capacity.

Virtual threads — parked tasks free carriers for other work

A virtual thread is a lightweight Java thread scheduled onto platform carrier threads. When it makes a supported blocking call, it parks, meaning it stops running and waits. Parking frees its carrier for other work. So many waiting tasks need not each hold an operating-system thread. This does not make one computation faster. It adds no CPU cores. It also does not protect shared changeable data from unsafe access.

Java feature and limits: On Java 21, blocking inside synchronized may pin a carrier. JDK 24 JEP (JDK Enhancement Proposal) 491 removes monitor-related pinning. Some native-code cases can still pin.

Semaphore — permits limit access to a resource

A Semaphore counts permits, like tokens allowing access to a limited resource. acquire() takes one permit, waiting if none remain. release() returns one and may let a waiting task continue. The programmer must pair these calls around resource use; the semaphore does not guard the code automatically. Unlike a lock, it records no owner, and extra releases can increase the count beyond its starting value.

Java feature and limits: Call acquire() before the try whose finally releases the permit. finally runs when that try exits, including after an exception. The default semaphore does not guarantee first-come service; each successful acquire() needs one release().

Semaphore — missing or extra releases break the limit

If a task ends without returning its permit, later callers may wait forever. To prevent this, call release in a finally block after acquire succeeds, so the permit returns even if the resource use throws. The opposite mistake is releasing when acquire was interrupted before it succeeded. That adds a permit the task never took, and too many tasks may enter. The diagram shows the counter and the waiting tasks, so a missing or extra release is visible.

Java feature and limits: A permit leak stalls the resource but does not necessarily form a deadlock cycle. The supplied runner already acquires before try and releases in finally.

Semaphore — trace permits, active users and waiting tasks

Starting with two permits limits the resource to two users if every acquire() and release() is paired correctly. Twenty virtual tasks can exist while only two use that resource. Follow the free-permit count: A and B enter, so C waits. When A releases a permit, C can enter after its own acquire() succeeds. The unit test records peak simultaneous users and requires at most two.

Java feature and limits: This shows one possible order of acquisition. A semaphore limits how many are inside at once, not requests per second or how many tasks are waiting. It does not promise first-come service.

Timing experiment — compare equal work, then elapsed time

Every mode runs the same 120 tasks. Three warmup rounds give Java a chance to prepare frequently used code. Five measured rounds rotate mode order so no mode always goes first. Accept a sample only if completed counts and checksums match. Time startup, execution and cleanup; print afterward. Compare simulated waiting and CPU computation separately.

Java feature and limits: Sleep simulates waiting; warmup does not prove stable performance. This is a classroom comparison, not a Java Microbenchmark Harness (JMH), production-service or memory benchmark.

ReentrantLock — track ownership and release the lock

A ReentrantLock has one owner and counts how often that owner acquires it. Reentrant means the same thread can acquire it again. Each unlock() reduces that count; the last releases the lock. Other threads wait. lockInterruptibly() allows interruption to end an acquisition wait. A timed tryLock() can return false without acquiring anything. After acquisition succeeds, use finally to release the lock.

Java feature and limits: Only the owner may unlock. A timed tryLock() that returns false gives no ownership, so that caller must not unlock. The default nonfair lock does not guarantee arrival-order service.

Dining philosophers — each worker waits for the next fork

Deadlock means threads cannot continue because each waits for another in the group. P0–P4 name five philosophers, and F0–F4 name their forks. Each philosopher needs its own numbered fork and the next one, wrapping from F4 to F0. If all hold the first fork and request the next, their waits form a circle. The demonstration arranges this state, records five first forks held, then interrupts and joins every worker.

Java feature and limits: A timeout alone does not prove deadlock. The recorded ownership snapshot explains the cycle. Recovery must release every lock that was acquired.

Interruption — stop and join the deadlocked demonstration workers

A classroom deadlock demonstration must end safely. After the five first-fork owners and their second-fork attempts are set up, the caller interrupts every worker before joining any of them. The workers use interruptible lock acquisition and finally blocks, so they stop waiting and release the locks they really hold. The caller then calls join with a time limit on each worker and checks isAlive(). Interrupting only requests a stop. Seeing the workers terminate shows cleanup finished.

Java feature and limits: An interrupt asks for cooperation and never forces a stop. Release only locks actually acquired. A timed join can return while a worker is still alive, so the isAlive() check matters.

Global lock order — take the smaller fork first

A global lock order means every worker takes shared resources in the same fixed order. Each philosopher picks up the lower-numbered fork first and the higher-numbered fork second, so P4 takes F0 before F4. A circular wait would need numbers to climb and then return to a smaller one, which this rule forbids. In the picture, P0 is eating while its neighbours wait for forks P0 owns exclusively.

Java feature and limits: The animation illustrates a possible state, not live Java execution. Lock ordering prevents circular deadlock. It does not guarantee freedom from starvation: a worker might repeatedly miss access while others continue.

BlockingQueue — items, producers, consumers and waits

A BlockingQueue transfers items from producers, which add them, to consumers, which remove them. A bounded queue limits stored items. put() waits for space when full; take() waits for an item when empty. ArrayBlockingQueue keeps first-in, first-out order: remove the oldest item first. Waiting releases the queue’s internal lock. Basic use needs no additional synchronized block.

Java feature and limits: Capacity limits stored items, not all application tasks. Timed offer() returns false and timed poll() returns null on timeout; handle both results explicitly.

BlockingQueue — an outer monitor can cause deadlock

An outer monitor can break queue coordination that is otherwise correct. Suppose the queue is full. Producer P holds appLock and waits inside put for space. Consumer C needs appLock before it can call take, so C cannot free any space. put releases the queue’s internal lock while waiting, but never appLock. Remove the unrelated outer monitor from blocking queue calls. Use timed offer or poll when you need a limited wait and an explicit failure plan.

Java feature and limits: This is an illustrative failure, not the supplied queue example. A timeout reveals missing progress; handle the item or failure explicitly instead of silently dropping it.

BlockingQueue — a full buffer makes the producer wait

A BlockingQueue coordinates handoff between producers and consumers. With capacity two, items A and B fill the queue, so put(C) cannot finish until the consumer removes an item. This slowing of the producer when downstream is full is called backpressure. Handing data through the queue also makes the producer’s writes visible to the consumer. The example returns A, B and C in order, with no polling or sleep-based coordination.

Java feature and limits: A latch counted down just before put shows the producer reached that line, not that it is already blocked. Queue capacity does not limit all running tasks.

CPU work — runnable tasks share limited processor capacity

A CPU-bound task spends most of its time computing rather than waiting. The picture uses two CPU slots and four tasks to show limited capacity. The instructor’s actual machine reports sixteen processors. Platform and virtual threads both compete for that processor time. Check that tasks finished and results were collected before reading any timings. More runnable tasks do not add cores. The real scheduler may switch among them in short time slices.

Java feature and limits: This simplified schedule shows capacity, not a universal finishing order. The real workload gives identical inputs to every strategy and requires no speed ranking.
