2. The problem: starting is not completion

We want a console example that returns the actual executing worker name. The caller starts a platform worker, which records its name into a shared result. If the caller reads immediately, that read can happen before the worker stores anything. This timeline illustrates one possible schedule; it is not a recorded unsafe run or a method supplied by the reference.

3. The solution: start, join, then read

Start schedules another execution path. Join waits for that worker to terminate, and a successful return establishes visibility of the worker actions to the caller. Read the result afterward. In the separate direct-call case, run executes on the calling thread, so it records the caller name.

4. Lifecycle source, statement by statement

Actual excerpt of Lifecycle.startAndJoin:

AtomicReference<String> result = new AtomicReference<>();
Thread worker = Thread.ofPlatform().name("lesson-worker").unstarted(
        () -> result.set(Thread.currentThread().getName()));
worker.start();
worker.join(); // Completion is established before the caller reads the result.
return result.get();
StatementWhat it does
new AtomicReference<>()Creates the one object shared by caller and worker. It starts as null.
Thread.ofPlatform().name(...)Builds a platform thread with the name lesson-worker.
.unstarted(lambda)Creates the thread without scheduling it. Nothing has run yet.
lambda bodyRuns on whichever thread executes it. It reads Thread.currentThread().getName() there and stores the name in the reference.
worker.start()Asks the JVM to schedule the worker. The caller continues at once. When the worker runs is up to the scheduler.
worker.join()The caller blocks until the worker terminates.
result.get()Reads the value after join has returned.

Now the actual directRun excerpt:

Thread worker = Thread.ofPlatform().name("unused-worker").unstarted(
        () -> result.set(Thread.currentThread().getName()));
worker.run(); // A normal method call stays on the caller's platform thread.
return result.get();

It uses the same shape, with a fresh AtomicReference and the name unused-worker. It calls run() instead of start().

What is shared

Only the AtomicReference is shared. The lambda captures it. The caller and the worker both hold a reference to the same object.

What start schedules

start makes a new execution path eligible to run. It does not say when the path runs, how fast, or in what order its output appears relative to the caller.

What join guarantees

When join returns normally, the worker has terminated. The Java memory model also says that every action in the worker happens-before a successful return from join on that thread. The caller therefore sees the worker's writes. Here the written value is the name, and the caller reads it after the join.

Why run stays on the caller

run() is an ordinary method call on a Thread object. It starts nothing. The lambda executes inside the calling thread, so Thread.currentThread().getName() returns the caller's name. The name unused-worker is never observed.

What AtomicReference guarantees independently

AtomicReference gives atomic and visible get and set operations on that one reference. Taken alone, it would make the stored value safely visible. It does not make the caller wait. Without join, the caller could read null because the worker had not run yet. Visibility and completion are separate properties here, and join supplies completion.

Why the thread name is evidence, not synchronization

The name is data the task records about itself. It shows who executed the task. It does not order anything and does not make anything visible. Only join and the atomic type do that work.

7. Errors, interruption and timeouts

  • join throws InterruptedException if the caller is interrupted while waiting. startAndJoin declares it and does not hide it. In that case the worker's completion was not established.
  • join() has no inherent timeout. If the worker never ends, the caller waits forever.
  • The test's @Timeout(15) is a guard that fails a hung test after 15 seconds. It is not a runtime guarantee that startAndJoin will return in production use.
  • After a repair, rerun the same focused test first. Run the Main route again and refresh the HTML using the repaired source and fresh execution evidence before advancing.

Concurrency — four problems Java must coordinate

A task is a unit of work; a thread is an execution path that performs it. Concurrency means tasks overlap in lifetime, while parallelism means they execute simultaneously. Overlap introduces four practical questions: when work is complete, who may update shared state, how outcomes reach the caller and how workers acquire scarce resources. Each example isolates one of these questions.

Thread — identify the task, worker and completion boundary

A Thread object represents an execution path; its Runnable body describes the work. Creating an unstarted object does not execute that body. Start makes the worker eligible to run, while join lets the caller wait for termination. The result is separate shared data. The diagram connects these parts to their Java calls before the example compares a started worker with a direct run call.

Java boundary: The diagram introduces stable Java APIs. A Thread can be started only once; a direct run call creates no second execution path.

Thread — an unfinished worker can keep join waiting

A worker that never terminates can keep a caller inside join forever. This illustrative loop has no circular resource dependency, so its failure is nontermination. Cancellation must be part of the worker design: use finite work units, check cancellation, and leave through cleanup. A bounded join limits how long the caller waits, then an explicit liveness check determines whether the worker actually stopped.

Java boundary: Illustrative failure, not the supplied finite lifecycle task. Interruption and a timed join cannot force an arbitrary worker to stop.

Barrier and latch — name the participants and release condition

A CyclicBarrier lets a fixed number of peers meet at a reusable phase boundary. Our two counter workers finish their reads before either writes. A CountDownLatch instead counts one-shot signals down to zero; an awaiting caller continues only then. The participant count, waiting point and release condition are different parts of these mechanisms. Neither primitive collects a task value or reports its exception by itself.

Java boundary: The lost-update example uses a barrier; dining uses latches. A completion signal does not prove successful work, so observe failures separately.

Barrier and latch — missing signals need bounded failure handling

A missing participant can prevent a rendezvous from completing. If B fails before reaching a barrier, an untimed A can wait indefinitely. If a worker forgets its latch signal, the count may never reach zero. Use timed waits and observe task failures. A latch signal in finally can mean that a worker ended; Future results must still distinguish success from failure. A barrier timeout breaks that barrier phase and releases other waiters exceptionally.

Java boundary: Other waiters at a broken barrier receive BrokenBarrierException. A timeout reports incomplete coordination; it does not perform the missing work.

Race condition — both workers can overwrite one update

An increment reads the old value, calculates its successor and writes it back. Two workers can both read zero, then both store one. A barrier makes both reads finish before either write, forcing this lost update. Declaring the field volatile gives visibility and ordering guarantees for individual accesses; it does not make the complete read-modify-write sequence indivisible.

Synchronized — identify the monitor, block and blocked contenders

synchronized (lock) acquires the monitor associated with that particular object. Its braces enclose the protected block. One thread owns the monitor while other contenders wait to enter; their Java state is BLOCKED. Exiting the block normally or exceptionally releases the monitor. The same object must guard every access covered by the policy. The entry area below shows contenders, without promising their arrival order will be preserved.

Java boundary: The entry area is a conceptual contender queue, not Object.wait’s condition wait set. An instance synchronized method locks this; a static one locks its Class object.

Synchronized — an endless protected loop prevents entry

If A runs an unbounded loop while owning a monitor, B and C can remain blocked at entry. This is a monitor held indefinitely, without requiring a deadlock cycle. An interrupt does not automatically unlock the monitor or stop a loop that ignores cancellation. Move long computation or blocking work outside the critical section where the invariant permits it, and keep each protected update finite. Cancellation checks let the owner finish its work and leave.

Java boundary: Illustrative failure case. sleep also retains an owned monitor; synchronized entry has no built-in timed or interruptible acquisition API.

Synchronized — opposite nested lock orders create a true deadlock

A deadlock occurs when dependencies form a cycle that prevents every participant from progressing. A owns M1 and waits for M2; B owns M2 and waits for M1. Neither reaches its release boundary. Require one global acquisition order, such as M1 before M2, or remove unnecessary nested locking. Then a waiting worker cannot hold the later resource that the owner still needs. Keep protected work finite as a separate requirement.

Java boundary: Interrupting a thread blocked on synchronized entry does not abort that acquisition. The later ReentrantLock recovery example uses an explicitly interruptible API.

Monitor — serialize the complete counter update

A monitor gives one worker exclusive entry to a synchronized operation. Protect the read, calculation and write with the same monitor. While A updates the counter, B waits outside that operation. After A releases the monitor, B reads the new value rather than the old zero. The numbered trace follows two increments; either worker may acquire first without changing the final total.

AtomicInteger — identify the shared value and operation boundary

An AtomicInteger contains one shared integer and operations with specific guarantees. Get reads a value, set replaces it, and incrementAndGet increases it atomically and returns the new value. Both workers must address the same object. The boundary surrounds one operation, including the increment’s read and update. It does not automatically surround a sequence of separate calls or protect an unrelated field. There is no monitor-entry queue exposed by this API.

Java boundary: This is the API guarantee, without requiring a particular hardware instruction or implementation. Atomic operations do not promise scheduling fairness.

AtomicInteger — separate checks and updates can still race

Atomic methods do not make an entire check-then-act sequence atomic. With one ticket left, A and B can each read one before either decrements; two atomic decrements then produce minus one. CompareAndSet can condition the update on the expected value: only one change from one to zero succeeds. A failed contender rereads and rechecks the condition. A monitor around the whole decision or a semaphore for admission can express the same required invariant.

Java boundary: This illustrative ticket algorithm is not the supplied increment example. Retrying must refresh the expected value and condition; retries do not prove starvation freedom.

AtomicInteger — make one counter transition indivisible

AtomicInteger.incrementAndGet combines reading the counter and increasing it into one atomic operation. Concurrent calls take effect in a valid order even while their lifetimes overlap. In this trace A changes zero to one and B changes one to two. The caller waits for both tasks before checking the final count. The API supplies the atomic update without exposing intermediate local calculations.

ExecutorService — identify tasks, workers, queue and outcome receipts

An ExecutorService separates submitted work from the threads that execute it. Submit accepts a task and returns a Future receipt. A fixed pool reuses worker threads; pending tasks wait in its task queue until a worker is available. The caller can independently wait for the receipt’s outcome. Queue entries are tasks, not waiting threads. The diagram also names the lifecycle boundary: stop accepting work, finish or cancel outstanding work, and observe termination.

Java boundary: newFixedThreadPool(2) limits worker threads and uses an unbounded task queue. Executor close can wait for unfinished tasks; a Future is not a thread.

ExecutorService — bound the backlog and handle rejected work

Two busy workers do not bound the number of submitted tasks. With an unbounded queue, slow work can create growing latency and memory pressure. An illustrative ThreadPoolExecutor uses two workers and two queue slots, then rejects a fifth outstanding task through its AbortPolicy. The caller must handle that rejection, for example by returning a busy response or retrying within a deadline. Bounded admission makes overload visible while preserving the actual service capacity limit.

Java boundary: This bounded alternative is explanatory; the supplied shop aggregator uses a fixed pool and a small finite input. Rejection policy and caller handling must be designed together.

ExecutorService — dependent tasks can exhaust their own pool

A parent task can deadlock a one-worker pool by submitting its child to that same pool and waiting for the child’s Future. The child needs a worker, but the only worker belongs to the waiting parent. This thread-pool starvation deadlock is a dependency cycle. Submit independent tasks from the caller and collect them outside the exhausted pool, or perform the required child work directly. Adding a few workers does not remove arbitrary nested blocking dependencies.

Java boundary: Illustrative one-worker failure, not the supplied two-worker quotes implementation. The caller must remain outside the pool whose capacity its awaited tasks require.

Future — identify pending, successful, failed and cancelled outcomes

A Future is a receipt for an eventual outcome. Get can wait, return a value or throw an exception representing failure or cancellation. IsDone includes successful, failed and cancelled completion, so it cannot establish success alone. A timed get bounds that caller wait without automatically cancelling the task. Timed invokeAll has a different contract: it cancels unfinished tasks at the batch deadline. Our aggregator inspects cancellation before collecting values.

Java boundary: Cancelled get throws CancellationException. The supplied aggregator instead checks isCancelled and throws its own TimeoutException; cancellation does not establish worker termination.

Cancellation — a cancelled Future can leave work running

A cancelled receipt can coexist with a task that still runs. Cancel with interruption requests cooperation; it does not forcibly terminate an arbitrary computation. If the task ignores interruption, executor close may continue waiting. Use finite work units, cancellation checks and interruptible operations where available, then release resources in finally. After requesting cancellation, observe termination through an appropriate bounded wait and handle a still-running worker explicitly.

Java boundary: Illustrative failure: the supplied waits cooperate. shutdownNow also requests interruption; it does not force tasks to stop or prove cleanup.

ExecutorService — submission and completion are separate

A Callable returns a value or throws an exception. An ExecutorService assigns tasks to workers; a Future represents an eventual outcome. Three quote lookups can share two platform workers, with the remaining task waiting for capacity. The caller collects each result through get. That operation exposes task failures and provides the documented visibility boundary for the completed work.

Task outcomes — values, failures and deadlines reach the caller

A batch can return values, fail inside a task or reach its deadline. Future.get wraps task failures in ExecutionException, preserving the cause. Timed invokeAll cancels unfinished tasks; our aggregator converts that state into TimeoutException. Interruption requests cooperative cancellation, so cleanup must observe worker termination. The three branches below explain what the caller receives.

Virtual threads — identify task, Java thread, carrier and processor

A virtual-thread executor creates a Java virtual thread for each task. While executing, that virtual thread mounts on a platform carrier thread, which runs through an operating-system thread on available processor capacity. Supported waiting can unmount the virtual thread while preserving its identity and stack. Parked tasks sit outside the active carrier mapping. The scheduler can later mount a ready virtual thread on an available carrier, including a different one.

Java boundary: The carrier count is illustrative. Virtual threads do not add processor cores, database connections or correctness guarantees; create one per task rather than pooling virtual threads.

Virtual threads — distinguish pinning from resource-capacity limits

On Java 21, a virtual thread that blocks while inside synchronized can retain its carrier through pinning. Other runnable work cannot use that occupied carrier in the illustrated state. Keep protected updates short and move blocking work outside where correct; an explicit lock can suit Java 21 coordination. JDK 24 removes monitor-related pinning, while some native-code situations remain. Independently, cheap waiting still requires a semaphore or other policy around scarce dependencies.

Java boundary: The version boundary is JEP (JDK Enhancement Proposal) 491 in JDK 24. Pinning is not itself a circular deadlock, and a runtime upgrade does not increase an external service’s capacity.

Virtual threads — waiting tasks can share carriers

A virtual thread is a lightweight Java thread scheduled over platform carrier threads. A supported blocking operation can park it and release its carrier for other work. This makes many waiting tasks practical without dedicating an operating-system thread to each one. It does not accelerate an individual computation, add CPU cores or synchronize access to shared mutable state.

Semaphore — identify permits, resource users and waiting tasks

A Semaphore keeps a permit counter. Successful acquire consumes a permit; when none remain, a caller waits before entering the resource operation. Release returns capacity and can enable a waiting task. The protected region is application code between those calls, so correct pairing is the application’s responsibility. A semaphore differs from an ownership lock: it does not track which thread owns a permit or enforce the initial count as a maximum.

Java boundary: Acquire precedes the try whose finally releases the permit. The default constructor does not promise FIFO service; extra releases can exceed the intended limit.

Semaphore — leaks and extra releases break the capacity policy

A task that exits without returning its acquired permit can leave later callers waiting indefinitely. Release in finally after a successful acquire, so exceptional resource use still returns capacity. Conversely, if acquire was interrupted before success, releasing adds a permit that was never obtained. This can let too many tasks enter. The diagram shows both the counter state and the waiting tasks, making the missing or extra release visible.

Java boundary: A permit leak is a resource stall, without necessarily forming a deadlock cycle. The supplied runner already acquires before try and releases in finally.

Semaphore — track permits, users and waiting tasks

A Semaphore supplies a fixed number of permits around a scarce dependency. Twenty virtual tasks can exist while only two enter the protected section at once. Follow the free-permit count as A and B enter, C waits, and A releases capacity. C enters only after successfully acquiring a permit. The unit test records peak simultaneous resource use and requires it to stay within two.

Timing experiment — compare equal work before elapsed time

Every strategy receives the same 120 tasks and simulated wait. Three warmup rounds prepare execution, then five measured rounds rotate mode order to reduce a fixed-order bias. Accept a sample only after result counts and checksums agree. Include startup, completion and cleanup in elapsed time; keep printing outside that timer. A separate CPU workload tests interpretation when work computes instead of waiting.

ReentrantLock — identify ownership, hold count and explicit release

A ReentrantLock has an owner and an acquisition count. Its owner can acquire it again; matching unlock calls reduce that count until the final release makes the lock available. Other contenders wait outside the protected operation. LockInterruptibly supports interruption during acquisition, and timed tryLock can report that acquisition failed. These calls make waiting policy explicit, while a finally block still supplies reliable release after success.

Java boundary: Only the owner may unlock. A false timed tryLock result gives no ownership and requires no unlock; the default nonfair lock promises no arrival-order service.

Dining philosophers — each worker waits for its neighbour

Deadlock means a group of tasks cannot progress because each waits for another in that group. Philosopher Pi needs forks Fi and F(i+1)%5. If every philosopher holds Fi before requesting the next fork, their requests close a circular wait. We will coordinate that state deliberately, record five first forks held, then interrupt and join every worker so the demonstration can finish.

Interruption — recover the controlled circular wait

A classroom deadlock demonstration must finish safely. After coordinating five first-fork owners and their second-fork attempts, the caller interrupts every worker before joining any worker. Interruptible acquisition and finally blocks let workers stop waiting and release their actual locks. The caller then performs bounded joins and checks every worker’s liveness. Interruption requests recovery; observing termination establishes that cleanup completed.

Global lock order — acquire smaller fork before larger fork

A global lock order makes every worker acquire resources in the same strict order. Each philosopher takes the lower-numbered fork first and the higher-numbered fork second; P4 therefore takes F0 before F4. A cycle would require increasing numbers to return to a smaller starting point, which the rule forbids. The illustration shows P0 eating while neighbours wait for its exclusively owned forks.

BlockingQueue — identify buffer, producer, consumer and wait conditions

A BlockingQueue transfers items between producers and consumers. Capacity limits pending items in the buffer. Put waits for space when that buffer is full; take waits for an item when it is empty. The supplied ArrayBlockingQueue preserves first-in, first-out order. Its internal coordination lets a waiting operation release the internal queue lock. An unrelated external monitor is unnecessary for these basic thread-safe operations.

Java boundary: Queue capacity bounds pending items rather than every task in the application. Timed offer and poll need explicit handling of false or null.

BlockingQueue — an external monitor can close a deadlock cycle

An external monitor can defeat otherwise correct queue coordination. With a full queue, producer P holds appLock and waits inside put for space. Consumer C needs appLock before it can take an item, so C cannot free that space. Put releases the queue’s internal lock while waiting, but it does not release appLock. Remove the unrelated outer monitor from blocking queue calls; use timed offer or poll when a bounded wait and explicit failure policy are required.

Java boundary: Illustrative failure, not the supplied queue example. A timeout exposes missing progress; handle the item or failure explicitly rather than dropping it silently.

BlockingQueue — a full buffer slows the producer

A BlockingQueue coordinates transfer between producers and consumers. With capacity two, A and B fill the queue; put(C) cannot complete until the consumer removes an item. This backpressure slows production when downstream capacity is exhausted. Queue handoff also supplies a visibility guarantee for transferred data. The example should return A, B and C in order without polling or sleep-based coordination.

CPU work — runnable tasks share finite execution capacity

A CPU-bound task spends most of its lifetime computing. The illustration uses two CPU slots and four tasks to make execution capacity visible; the actual instructor machine reports sixteen processors. Both platform and virtual tasks compete for the machine’s available execution time. Follow task completion and result collection before interpreting timings. Adding runnable tasks does not add cores, and the real scheduler may interleave them through time slicing.
